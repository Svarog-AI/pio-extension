# Glossary

## Terms

- **Capability** — An AI-driven workflow unit (e.g., `create-goal`, `execute-task`, `quality-gate`) implemented as a directory package under `src/capabilities/<name>/`. Exposes a tool (`pio_<name>`, agent-callable) via `register(pi)` in `config.ts`. No capability command handlers exist — users interact through tools or TUI-only commands (`/pio-next-task`, `/pio-parent`). Each has a `CapabilityPackageConfig` (default export from `config.ts`) defining its session shape. Non-AI capabilities are consolidated in `direct-tools.ts`.
- **Capability Package** — Directory-based capability structure: `config.ts` (CapabilityPackageConfig + register), `role.md`, `workflow.ts`, `guidelines.md`, optional `callbacks.ts` and `schemas.ts`. Replaces the old single-file pattern (`CAPABILITY_CONFIG: StaticCapabilityConfig` in a `.ts` file). Auto-discovered by `discoverCapabilities()`.
- **CapabilityPackageConfig** — The config type for directory package capabilities. Defined in `capability-package.ts`. Fields: `name`, `skills`, `contract` (mandatory), `readOnlyFiles`, `writeAllowlist`, `allowProjectWrites` (opt-in, default `false` — permits project file writes during validation), `prepareSession`, `postValidate`, `postExecute`, `preValidate`. Default-exported from `config.ts`. The `CapabilityContract` inside the config may optionally declare `markers?: MarkerDeclaration[]` for declarative marker management.
- **Direct Tools** — Non-AI capabilities consolidated in `src/direct-tools.ts`: init, delete-goal, list-goals, parent, create-issue, goal-from-issue, pio_transition. Have no prompts, no sub-sessions, no validation hooks. Exported as `setupDirectTools(pi)`.
- **Goal workspace** — A directory under `.pio/goals/<name>/` containing all artifacts for a single feature/fix: `GOAL.md`, `PLAN.md`, step folders (`S01/`, `S02/`), and state markers.
- **Step folder** — A zero-padded directory inside a goal workspace (`S01/`, `S02/`) containing the specification (`TASK.md`), implementation artifacts (`TEST.md`, `SUMMARY.md`), review output (`REVIEW.md`), and optionally a `subgoals/` subdirectory for nested subgoal workspaces.
- **prepareSession hook** — A `PrepareSessionCallback` defined on `CapabilityPackageConfig.prepareSession` that runs during the `resources_discover` phase, before `before_agent_start`. Used by capabilities to enrich runtime config at startup — e.g., `execute-task` and `review-task` read per-step skills from TASK.md frontmatter and merge them into config via `mergeCapabilitySkills()` from `capability-utils.ts`.
- **Sub-session** — An isolated pi agent session spawned by `launchCapability()`. Contains a custom `pio-config` entry with prompt, working directory, validation rules, and file protections. Runs one capability per session.
- **Transition** — The resolution of "what runs next" after a capability completes. Handled by the declarative state machine framework (`state-machines.ts`): edges with `resolve(context, params) → TransitionResult | undefined` replace imperative switch statements. `dispatch()` iterates outgoing edges and collects all matches. Resolvers can return `cleanup: string[]` to declaratively delete signal files consumed by transitions.
- **StateMachine** — Generic type `StateMachine<C>` from `state-machines.ts`. Named config with `id`, `name`, `description`, and `edges: TransitionEdge<C>[]`. The default `goalDrivenDevelopment` machine exports 12 edges covering the pio workflow, including two blocked-step transitions (`execute-task → evolve-plan` and extended `review-code → evolve-plan`). Registers explicitly via `setupPioWorkflowMachine()` called from `index.ts`. Machine registry backed by `_machinesById` Map with O(1) lookup via `getMachine(id)`.
- **ResolverResult** — Type `Omit<TransitionResult, "stateMachineId">` from `state-machines.ts`. The return type for edge resolver functions — `stateMachineId` is omitted because `dispatch()` auto-injects it. Includes optional `cleanup?: string[]` field: an array of input spec names from the completing capability's contract, resolved and deleted by the exit lifecycle (`runExitLifecycle`) via CapState after transition dispatch.
- **TransitionEdge** — Generic type `TransitionEdge<C>` from `state-machines.ts`. Directed edge `{ from, to, resolve }` where `resolve` is a function combining condition check + param computation. Returns `ResolverResult` when firing, `undefined` otherwise.
- **TransitionResult** — Type `{ capability, stateMachineId, params? }` identifying which machine produced the result and which capability should run next. `stateMachineId` is guaranteed by `dispatch()` (auto-injected via `{ ...result, stateMachineId: m.id }`), not set by resolvers. Used by the exit lifecycle (synthesized `__pio-exit` phase → `runExitLifecycle`) for auto-transition routing.
- **Declarative State Machine Framework** — The transition system in `state-machines.ts` (replaced `state-machine.ts`). Iteration-based dispatch with no switch statements. Supports explicit machine dispatch (`getMachine(id)` + `dispatch(machine, ...)`) and fallback multi-machine dispatch via `dispatch(undefined, ...)`. The exit lifecycle (`runExitLifecycle`) reads `stateMachineId` from session params to dispatch against the correct machine. The `stateMachineId` is propagated at top level in enqueued task params.
- **pio_transition Tool** — Non-AI tool registered in `direct-tools.ts`. Manual override for transitions: enqueues a task and records the transition audit entry. Used when auto-resolution is undesirable or multiple matches exist.
- **CapState** — Contract-backed lazy file access (`capability-state.ts`). Wraps a `CapabilityContract` with base directory and params. API: `.input<T>(name)` looks up a named input file; `.output<T>(name)` looks up a named output file; `.undeclared(path)` accesses marker files not in any contract (passes explicit `projectRelative: false`); `.resolvePath(entry: MarkdownFileSpec)` is the unified resolution method all accessors flow through — handles `projectRelative` entries, placeholder resolution, and workspace prefix injection. Entry maps store full `MarkdownFileSpec` references (not copies). Public `.contract` getter exposes the wrapped contract. Every `MarkdownFileSpec` must declare a required `name: string`. Duplicate names across inputs/outputs throw at construction **unless** they share the same name and file path — in that case, the second registration is silently deduplicated (first wins). Enables multiple OneOfGroups to reference the same output entry. Replaces the old `GoalState` (deleted).
- **CapabilityContract** — The unified contract type (`types.ts`) mandatory on all capability configs. Declares `inputs[]`, `outputs[]` (with optional `schema`, `requiredWhen`, `projectRelative`), `markers[]` (optional, declarative marker configuration), and `excludedFiles[]`. Replaces old separate types: `FrontmatterSchemaDeclaration`, `ValidationRule`, `InputValidationSpec` (all deleted).
- **MarkerDeclaration** — Interface (`types.ts`) for declarative marker configuration. Fields: `outputFile: string` (matches a contract output name), `field: string` (frontmatter key to check), `values: Record<string, string>` (maps frontmatter value → marker filename). Used by the framework marker engine (`applyMarkers`, `cleanupMarkers`), which is colocated in `guards/mark-complete.ts` (module name retained) and invoked from `runtime/exit-lifecycle.ts` at exit. Both execute-task and review-task use this pattern.
- **MarkdownFileSpec** — Entry in a `CapabilityContract` declaring a file: `{ name, file?, paramKey?, schema?, requiredWhen?, projectRelative? }`. `name` is mandatory (kebab-case). `file` is optional when `paramKey` is set. `paramKey?: string` enables dynamic path resolution from `params[paramKey]` at runtime — static `file` serves as fallback/label. `requiredWhen` signature is `(params?, capState?) => boolean` — predicates can read contract inputs (via CapState) to make output requirements dynamic. `projectRelative: true` resolves from global `pioRootDir` (`<cwd>/.pio/`) instead of the workspace directory. Used by capabilities like `finalize-goal` and `project-context` to access `.pio/PROJECT/*.md` files.
- **pioRootDir** — Plain `const` in `fs-utils.ts` resolving to `<cwd>/.pio`. Known at module load time, never changes at runtime. Used for `projectRelative` path resolution.
- **GoalState** — *DELETED.* Was a lazy-evaluated filesystem view over goal workspaces. Replaced by CapState.
- **COMPLETION_SUMMARY.md** — Content-bearing file (replaces empty `COMPLETED` marker) written by evolve-plan when all plan steps are specified. Includes YAML frontmatter (`status: "complete"`) and a markdown body explaining completion reason. Consumed by the quality-gate capability as its requirements input, then deleted via resolver-declared cleanup.
- **QUALITY_GATE.md** — Output of the `quality-gate` capability. Includes YAML frontmatter with `status: "approved" | "rejected"`. When approved, finalize-goal reads this file (replacing COMPLETION_SUMMARY.md). When rejected, revise-plan reads this file as revision context.
- **Validation gate** — Engine-side validation at session exit: when traversal reaches the end of a workflow, the synthesized `__pio-exit` terminal code phase runs `runExitLifecycle()` (`runtime/exit-lifecycle.ts`), which verifies expected output files exist via contract-based `validateOutputs()` before applying markers, dispatching transitions, and enqueuing the next task. All outputs, including `COMPLETION_SUMMARY.md`, are validated through the contract mechanism via `requiredWhen` predicates (no special-case short-circuits). The former `pio_mark_complete` tool was removed — exit is automatic; on failure the session pauses in ad-hoc mode with no automatic retry.
- **File protection** — Two mechanisms enforced via the `tool_call` event handler:
  - *Read-only files:* Certain files (e.g., TASK.md, TEST.md during execution) cannot be modified
  - *Write allowlist:* Only explicitly allowed paths may be written to; blocks all writes to `.pio/` outside the session's goal workspace
- **Session queue** — Per-goal task slots at `.pio/session-queue/task-{goalName}.json`. One pending task per goal. Files are consumed (deleted) when launched by `/pio-next-task`.
- **Agent refinement loop detection** — A session-guard feature that tracks turn count during pio sessions. When `turnCount` reaches the configured `turnThreshold` (default: 15), it sends a one-time nudge via `pi.sendUserMessage({ deliverAs: "steer" })` encouraging self-diagnosis. The counter resets after each nudge, enabling periodic reminders. Configurable via `guards.turnThreshold` in `~/.pi/pio-config.yaml`. Uses `"steer"` so the nudge interrupts the agent after the current turn's tool calls (mid-run) rather than waiting for the full run to complete.
- **Model config** — Optional `~/.pi/pio-config.yaml` that overrides which LLM model a capability uses. Resolution: per-capability → default → inherit parent.

- **Finalize Goal Agent** — The agent that runs after a goal is fully completed. Reads accumulated decisions from DECISIONS.md, per-step SUMMARY.md files, and PLAN.md, then evaluates each finding against update rules to determine which `.pio/PROJECT/*.md` files need updates.
- **CapabilitySkills** — The config shape for declaring skills per-capability: `{ mandatory?: string[], recommended?: { name: string; condition: string }[] }`. Both fields optional. Defined in `src/types.ts`. Mirrored structurally by `TASK_FRONTMATTER_SCHEMA` in capability-local schemas.
- **Auto-discovery** — `discoverCapabilities(baseDir)` scans `src/capabilities/` for directories containing `config.ts`, dynamically imports configs, and returns `CapabilityPackageDescriptor[]`. Test fixtures (`test-*` prefixed) are filtered out. Replaces hardcoded per-capability imports in `index.ts`.
- **Prompt Compiler** — `prompt-compiler.ts` exports `compilePrompt()` which reads component files from capability package directories (`role.md`, `workflow.ts`, `guidelines.md`) and assembles the final prompt. Also exports `readWorkflowPhases()`, `renderWorkflowPhases()`, `mergeWorkflowPhaseSkills()`, `readPackageComponents()`. Strict leaf module.
- **Step Nudging** — *DELETED.* Was `guards/step-nudging.ts` with a `workflow-step-finish` tool. Replaced by the runtime loop engine (`src/runtime/loop-engine.ts`).
- **Phase** — A unit of workflow execution within a capability session (not to be confused with a plan "step" in PLAN.md). Renamed from the ambiguous term "step" to disambiguate workflow execution phases from PLAN.md implementation steps. Types: `WorkflowPhase`, `WorkflowPhaseSkillDeclarations`. State fields: `currentPhase` (numeric, backward compat), `currentPhaseId` (string, primary navigation key), `totalPhases`, `phasesList`. Phases are accessed via PhaseManager (registry by string ID) instead of direct array indexing. Kind values: `"standard"`, `"variable-definition"`, `"branch:if"`, `"branch:switch"`, `"loop"`, `"code"`.
- **`branch:if` Phase** — A `WorkflowPhase` with `kind: "branch:if"`. Executes as a programmatic phase (inline, no agent turn) that evaluates `condition?: (state: PioSessionState) => boolean | unknown` and routes to either the `then` or `else` arm. Only callback form is supported — no string expression syntax. The `then` arm must be non-empty; empty `else` resolves to skip (arm-first = post-branch ID). Declares nested phases via `then?: WorkflowPhase[]` and `else?: WorkflowPhase[]`. After PhaseManager flattening, routing data lives in `_conditionalRouting` as `IfBranchRouting`.
- **`branch:switch` Phase** — A `WorkflowPhase` with `kind: "branch:switch"`. Executes as a programmatic phase that evaluates `on?: ((state: PioSessionState) => unknown) | string` and routes to the matching case in `cases?: Record<string, WorkflowPhase[]>` or `defaultBranch?: WorkflowPhase[]`. Supports two `on` forms: callback (evaluates directly) and `$varName` string form (resolves via `state.store?.get(varName)`). Uses loose equality (`==`) for null/undefined handling — both fall through to default. Declares nested phases via `cases` and `defaultBranch`. After PhaseManager flattening, routing data lives in `_conditionalRouting` as `SwitchBranchRouting`.
- **`loop` Phase (`kind: "loop"`)** — A do-while loop block: a multi-phase repeating unit. Fields: `body?: WorkflowPhase[]` (the repeating unit; missing/empty body throws path-aware `TypeError` at flattening) and optional `repeatWhile?: (state) => boolean | unknown` (same shape as `condition`; truthiness evaluated, throwing → warn + fail-safe exit, omitted → always repeat). The container links unconditionally to `body[0]` (≥1 full pass guaranteed — the condition is never pre-checked); `repeatWhile` is evaluated at the end of each full body pass. `maxIterations` counts **full body passes** and restricts repeats only: repeat allowed iff `passes + 1 < resolvedMax` (cap check precedes condition evaluation; cap exit silent; missing state → warn + exit). Programmatic (`isProgrammatic()` → true — containers never get agent turns); all-programmatic bodies run inline within one `advancePhase()` call and terminate at the cap. After PhaseManager flattening, repeat/exit data lives in `_conditionalRouting` as `LoopBackRouting` keyed by the synthetic loop-end merge node id (`__loop-end-<id>`), not the body tail — each loop's distinct routing entry is what makes nested loops route correctly.
- **BranchRouting** — Union type `IfBranchRouting | SwitchBranchRouting | LoopBackRouting` from `workflow-types.ts`. Represents post-flattening routing data for conditionally-routed phases: `IfBranchRouting = { thenFirst: string; elseFirst?: string }`, `SwitchBranchRouting = { caseFirst: Record<string, string>; defaultFirst?: string }`, `LoopBackRouting = { loopTarget: string; exitTarget?: string; repeatWhile?; maxPasses?: number; loopId: string }` (do-while repeat/exit data installed on the synthetic loop-end merge node — structurally discriminated like the others, no `type` field; runtime keys on `"loopTarget" in routing`). Stored in PhaseManager's `_conditionalRouting: Map<string, BranchRouting>`. All arm-first values are concrete strings — empty arms converge on the branch-end merge node during flattening. Naming convention: "Routing" (not "Target") because these types hold multiple destinations.
- **Runtime Loop Engine** — `src/runtime/loop-engine.ts` replaces prompt-based step nudging. Each workflow phase executes as one or more *agent runs* (iterations) with enforced bounds: `minIterations` (per-phase, default 1), `maxIterations` (resolution: per-phase > global config > built-in default of 15). After each iteration, evaluates `terminateWhen` conditions against `StepState` (`filesWritten[]`, `filesEdited[]`, `askUserCalled`). Phase lookups via PhaseManager.getPhase(currentPhaseId) instead of direct array indexing. Commands: `/goto <phase-id>` for manual phase jumps (with autocomplete and isIdle guard), `/continue` to exit ad-hoc mode. All phase content delivered via CustomMessage injection with type `"workflow-phase-instructions"` — KV cache safe. The `workflow-step-finish` tool was removed; advancement is automatic.
- **SessionVariableStore** — `src/runtime/session-store.ts`: two-layer variable system (read-only session params + writable runtime vars) with `${name}` template interpolation, type enforcement, and value coercion. Lives on `PioSessionState.store`, accessed via `getState().store`. Exposes three agent-facing tools: `setVar` (phase-gated), `getVar`, `listVars`. Writable vars persisted as `{ value, type }` per variable; read-only params never written to disk. NOTE: `pio/src/capability/pio-session.ts` declares a DELIBERATELY MINIMAL same-named local class (Map-backed `get/set/list`, insertion-ordered keys) — different package, different surface; the later setVar-family step wraps THAT store with typed getters/coercion, not the root one. NOTE UPDATED (goal `variable-model-redesign`): the `pio/`-side store is now DISSOLVED OUTRIGHT — the no-store variable model (**Variable cell** / **Phase variable binding**) replaced it; the root-tree system above stands UNCHANGED (different world — untouched by that goal).
- **Phase Variable** — Declaration on a variable-defining phase (`PhaseVariable`): `name`, `type` (`'string' | 'number' | 'boolean' | 'array' | 'object'`), `kind` (`'static' | 'llm' | 'computed'`), and optional `value`, `description`, or `compute`. Static vars set immediately; LLM vars set by agent via `setVar`; computed vars run callbacks during phase advancement.
- **Variable-defining Phase** — A `WorkflowPhase` with `kind: 'variable-definition'` and `variables?: PhaseVariable[]`. The loop engine generates a fixed template listing each variable instead of using freeform instructions. On validation failure (undefined vars), the phase loops with a follow-up listing missing variables.
- **Template Interpolation** — `${name}` placeholder resolution in `phase.instructions` and `phase.loopMessage` via `store.interpolate()`. Called in `buildPhaseInstructions()` for all phases when the store is available. Unresolved placeholders pass through unchanged. String values set via `setVar` are also interpolated before storage.
- **LoopWhileCondition** — Condition on `WorkflowPhase.loopWhile` (OR semantics: any passing callback keeps looping). Unified callback model: auto var completeness is generated as a default callback for variable-defining phases alongside user-defined conditions. Runs after `minIterations` floor but before `terminateWhen`.
- **StepState** — Structured state tracked per iteration in the loop engine: `filesWritten[]` (absolute paths of files written), `filesEdited[]` (paths edited via partial writes), `askUserCalled` (boolean). Reset at the start of each new iteration. Used only for termination condition evaluation.
- **TerminationCondition** — Condition definition on `WorkflowPhase.terminateWhen`: supports callback functions evaluated against `StepState`. AND logic — all conditions must return true to advance. Any condition returning false or throwing forces a loop replay.
- **PioSessionState** — Shared session state singleton (`src/runtime/session-state.ts`) persisting across all phases for the full capability session duration. Tracks `markCompleteCalled` (set by the engine-side `__pio-exit` exit wrapper when session exit completes — succeeded or threw-and-skipped; reset at turn start), current phase/iteration info (`currentPhase`, `currentPhaseId`, `totalPhases`, `phasesList`), `phaseManager` (PhaseManager instance, in-memory only), `projectRoot` (resolved project root for the per-phase write gate — in-memory only, set at `resources_discover` via `path.resolve(ctx.cwd ?? process.cwd())`; undetermined root fails safe by blocking non-contract writes), `sessionId` (unique session ID from `ctx.sessionManager.getSessionId()`, captured in `resources_discover`), `store` (SessionVariableStore), `loopPasses` (`Record<string, number>` — do-while repeat counters keyed by loop block id; required field, in-memory only, accumulates across re-entries, reset on session restart), in-memory-only automatic-exit fields (`programmaticLog`, `lastLlmPhaseId`, `exitOutcome`, `exitFailureMessage` — all excluded from the persistence projection), and refinement-loop counters. Reset between sessions via `resetState()`. Used by both the loop engine and the migrated session guard.
- **PhaseManager** — Module at `src/runtime/phase-manager.ts`. Owns phase registry (string ID → WorkflowPhase mapping) and next-phase resolution (`resolveNext`). Created during `resources_discover` via depth-first tree flattening of nested `WorkflowPhase[]`, stored on `PioSessionState.phaseManager`, never serialized. Uses two routing maps: `_routing` (linear successor links) and `_conditionalRouting` (branch arm first-phase IDs for `branch:if`/`branch:switch`). Public API: `getPhase(id)` for O(1) lookup, `resolveNext(currentId, state?)` — sequential via `_routing` for normal phases; evaluates conditions and jumps to correct arm for branch phases; `listIds()` returning all phase IDs (including nested children in DFS order); `getFirstPhaseId()` for engine startup. Replaces direct array indexing (`phasesList[currentPhase - 1]`) as the canonical phase access pattern.
- **currentPhaseId** — String field on `PioSessionState` tracking the active phase by ID alongside the numeric `currentPhase`. Defaults to `""` when inactive. Set during phase transitions, persisted in state-persistence JSON (required — old files without it are rejected). Primary lookup key for PhaseManager.getPhase().
- **/goto Command** — TUI command registered via `pi.registerCommand("goto", ...)` in loop-engine.ts. Takes a phase ID argument, validates against PhaseManager, jumps to the named phase (resets iteration to 1, clears tracking, persists, triggers follow-up). Guarded by `ctx.isIdle()` — blocked during active agent runs. Supports autocomplete via `getArgumentCompletions` callback with case-insensitive prefix matching.
- **Write Gate** — Phase-level write restriction enforced by the loop engine at `tool_call` events. Restricted-by-default: phases declare `write: [output-names]` on output-producing steps; phases without `write` cannot produce contract outputs (source code, tests, docs unaffected). Resolution is lazy and on-demand — one PhaseManager lookup + CapState resolution per write call (`phaseManager.getPhase()` + `capState.tryResolveOutput()`), no pre-built Map. Requires `capState` and `allContractOutputs` stored in PioSessionState. Also covers non-contract project file writes: the same gate blocks writes under the project root unless the active phase declares `allowProjectWrites: true` (default `false`). `/tmp/` paths and allowed contract outputs always pass; there is no `.pio/` exclusion (governed separately by capability-level validation). Complements the session-wide `CapabilityPackageConfig.allowProjectWrites` boolean in `validation.ts` — the phase field mirrors the `write[]` pattern with per-phase granularity. That LEGACY loop-engine gate (process-global singleton state under root `src/runtime/`) is the conceptual predecessor the new-runtime mechanism replaced by BEHAVIOR COPY (the extraction shares no code — the two trees run separate worlds): see **Per-session write gate**.

- **SessionExecutionState (per-session execution state)** — The dedicated LIFO companion module at the pio package TOP LEVEL `pio/src/session-execution-state.ts` (goal `per-session-write-gate`; owner-directed placement — NOT under `capability/guards/`, because producer/consumer modules straddle both domains). ## Business Concepts

- **Goal-driven workflow** — The core concept: complex work is structured as goals, each decomposed into a plan of ordered steps. Each step is specified (TASK.md with acceptance criteria), implemented test-first (executor derives tests from TASK.md using TDD), and reviewed (approve/reject) in isolated sub-sessions. Complex steps can be further decomposed via nested subgoals.
- **Specification-driven implementation** — `evolve-plan` produces TASK.md (what to build, with acceptance criteria) before any code is written. The executor (`execute-task`) derives test cases from the acceptance criteria using TDD methodology, then writes tests first and implements. This separates planning from execution and enables focused sub-sessions.
- **Subgoal lifecycle** — Complex steps marked `complexity: "subgoal"` in plan frontmatter spawn a child goal under `S{NN}/subgoals/<name>/`. The child runs the full pio lifecycle independently. On completion, `finalize-goal` propagates back to the parent's `evolve-plan`, which resumes the parent workflow via the session queue.
- **Review gate** — After implementation, `review-task` evaluates quality, test coverage, and alignment with requirements. Approval advances the workflow; rejection sends the step back for re-execution with feedback from REVIEW.md.
- **Quality gate** — Before finalization, `quality-gate` performs two user-decided checkpoints: E2E testing and code review. Produces QUALITY_GATE.md with frontmatter status (`"approved" | "rejected"`). Approved → finalize-goal; rejected → revise-plan. PR creation (if configured) happens here before the manual gates.
- **DECISIONS.md carryover** — Starting at Step 2, `evolve-plan` writes DECISIONS.md to document architectural decisions made during specification. Subsequent steps read this to maintain consistency across the implementation.
- **Transition audit trail** — Each capability completion records a transition entry in `<goalDir>/transitions.json`: an append-only JSON array tracking from→to transitions with timestamps and params. Provides observability into the workflow's progress.
- **Finalization gate** — After a goal completes, the finalize-goal capability reads accumulated decisions and updates `.pio/PROJECT/*.md` documentation. The pio-project-knowledge skill provides canonical update rules that map decision categories to target files. This ensures future goals benefit from accumulated knowledge.
